marco keeps every follow, block and list item on the network, 3.03B records, in a 44.1 GB snapshot on one box. An appview asks it graph questions while it renders a page. Does the viewer follow this author? Which of these 50 accounts block the viewer? Who are the mutuals?

An edge is a record, such as a follow, keyed by (actor, relation, rkey) and naming a subject. The out log keeps the actor's records in rkey order, so a follows page is a range and a delete by URI can find its subject. The in set keeps the subject's actors sorted, so "who follows this account?" and "does the viewer follow it?" are operations on sorted integers. Both views store u32 ids.

DIDs become u32 ids

The directory is every packed did:plc, sorted, and a DID's id is its position in it. Going from id to DID is an array index (15 B at id × 15). Going from DID to id is a search of one bucket. A did:plc is a hash, so the packed values are uniform. The top 22 bits pick one of 4.2M buckets in a 16.8 MB radix table, and a bucket holds about 10 packed DIDs to compare. Other DIDs and list URIs (3.8M of the network's 47.5M ids) stay strings in a sorted side table.

Ids are dense, 0 to 47.5M, so anything keyed by id is an array. The 64 shards are id ranges of about 742k ids, and each shard's index keeps 4 B per id saying where that id's list starts. A list names other accounts as u32s, 4 B where the DID string would take 32 B, and comparing two of them is one integer compare.

Out logs: records in rkey order

An out log is one actor's records in one relation, sorted by rkey. A TID rkey is a timestamp, so rkey order is time order, and newest-first paging with an rkey cursor needs no other index. Subjects are a plain u32 column, so any position reads in one load and a block's subjects can be scanned without touching rkeys. Rkeys are stored as the gap from the record before. Across the network's follows that's 4.00 B a record for subjects and 4.94 B for rkeys. An rkey that isn't a TID (0.014% of follows) is hashed into the same u64 with the top bit set and keeps its string in a side table.

A list of 4,096 records or more also carries a by-subject index: blocks of positions sorted by subject, with the subjects Elias-Fano coded (below). It costs 5.6 B for each record in such a list, 1.7 B averaged over every follow. In return, finding the record behind "does this mass-follow account follow X?" takes a by-subject page and an rkey page, where a scan could read all 886k subjects of the longest follow list.

In sets: Elias-Fano in blocks of 128

An in set is a subject's followers (or blockers, or the lists it's on) as sorted actor ids. marco cuts it into blocks of 128 and Elias-Fano codes each one from its first id, picking l from that block's own density. A value then costs l bits plus 2 to 3 bits. Membership never decodes the block. The probe's high part says which bucket to look in, a popcount over 64-bit words skips that many zeros, and only that bucket's low bits get compared.

Follower ids land all over the id space, since ids are positions in a hash-sorted directory. So an account with a few hundred followers takes about 2.5 B a follower, and the biggest account's 31M followers cost under half a byte each. Across the network, follows' in sets come to 2.1 B a pair, 2.2 B with heads, index and page padding. 92% of in sets have 128 members or fewer and fit one page. A probe into a bigger one binary-searches the first ids in its head and reads one block.

Changes since the snapshot: deltas and tombstones

The snapshot's lists are immutable, so a write never edits one. It goes to a delta for each list it changes: an out log's delta holds added records and deleted base records by rkey, and an in set's delta holds added and removed ids. Reads merge the delta over the base, and both stay sorted, so a merge is one pass over both.

A delete names only a URI, so the out log finds the subject. The pair leaves the in set only when no other record of the actor still names that subject (0.14% of follow records repeat a pair). Every delete also leaves a tombstone, the (actor, rkey) and the time the source saw it, so a create replayed from before the delete stays deleted.

A restart opens the snapshot and replays the segments written since the last checkpoint, which rebuilds the deltas. A checkpoint writes each changed list to a patch file behind its shard's base. A long list keeps its unchanged blocks in the base, and the shard's new index and heads point into both. Tombstones last until a checkpoint finds them older than anything a source still replays.

What lives in RAM

marco doesn't mmap the snapshot or use the kernel's page cache. Opening it reads the pinned sections whole and checks them: the directory, every shard's index and heads, and a 32-bit sum for each page. That's 2.1 GB for the whole network, and it's enough for any lookup to work out which pages it'll read. The other 42.0 GB are pages read with O_DIRECT into a cache that S3-FIFO manages, so a one-off scan doesn't push out the pages that keep getting read.

With 13 GiB for the 44.1 GB snapshot, 99.85% of requests never left their network thread, on a read mix weighted toward active viewers and much-liked authors. With 44 GiB, opening loads every page in 7.8 s and no request reads the disk after that.

The server also keeps two copies of the graph. They share every snapshot byte and differ only in their deltas. The writer applies a batch to the spare copy, swaps it in, then applies the same batch to the other once its readers have left, so a read never waits on a lock.

Lookups, step by step

Every lookup follows the same chain. The directory turns DIDs into ids, the id picks a shard and an index slot, and the slot leads to a list of up to 128 in one page or to a head in RAM. The head picks the blocks to read before any page is read. The costs below are measured on the whole network with every page in memory.
